# 图解模型

讲架构、流程、目录关系及修改时使用。普通无变化关系可继续用 `flow`、`graph` 或本地 SVG，不必制作三份相同画面。复杂拓扑拆成相关小图或制作静态 SVG。

```json
{
  "diagrams": [{
    "id": "entry-change",
    "title": "处理入口变化",
    "kind": "architecture",
    "direction": "LR",
    "note": "虚构的接法片段：只比较提交入口与处理职责，省略结果返回；改后尚待实施。",
    "nodes": [
      {"id":"page","label":"原页面＋状态查询","beforeLabel":"原页面","shape":"process","change":"modified"},
      {"id":"host","label":"原服务入口","shape":"process"},
      {"id":"worker","label":"任务处理","shape":"process","change":"added"}
    ],
    "edges": [
      {"from":"page","to":"host","label":"提交请求"},
      {"from":"host","to":"worker","label":"进程内调用","change":"added"}
    ],
    "groups": [{"id":"process","label":"同一服务进程","nodes":["host","worker"]}],
    "evidence": ["设计记录"]
  }],
  "verdict": {"label":"保留原入口","summary":"能力在现有进程内组合。","diagramId":"entry-change"},
  "sections": [{"id":"integration","title":"接法","subtitle":"新增能力放在哪里？","kind":"diagram","diagramId":"entry-change"}]
}
```

示例为字段片段，还需登记 `设计记录` 等必填报告字段；完整可运行输入见[专注阅读示例](../examples/focus-changes.json)。同一图可在不同章节引用，每次生成独立安全 ID，编号与来源保持一致。

## 字段

- `diagrams[]`：唯一 `id`、非空 `title`、`nodes[]`；可选 `kind: architecture | flow | tree`、`direction: LR | TB`、`edges[]`、`groups[]`、`note`、`evidence[]`、`outcomes`。
- `outcomes: {"before":"output","after":"output"}` 可为原生变化图登记一对关键结果节点（两侧也可用不同 ID）。填写时，两项都必须引用在自己视图中存在且可见的节点，例如改前不能指向新增节点。字段不额外渲染，也不要求结果是最后一个节点。结果明确时推荐登记；局部职责图、静态图或没有单一结果时，无需硬填。它不能判断两节点含义是否对应、路径能否到达或资料是否支持。
- 节点：唯一 `id`、短 `label`，可选 `shape`、`change`、`beforeLabel`、`evidence[]`。不同的改前标签必须标 `modified`；修改没有改标签时仍可用 `modified` 表示职责变化，具体差异写就近说明。
- 形状：`process`（默认，处理／组件）、`decision`（判断）、`terminator`（起止）、`store`（存储）、`data`（输入输出）。按语义选择，不为装饰凑图形。
- 变化：`unchanged`（默认，保留）、`added`（新增）、`removed`（移除）、`modified`（修改）。节点和边均可标；新增／移除节点的相关边也应如实标记。
- 边：有效 `from`、`to` 和解释机制的短 `label`；可选 `change`、`style: solid | dashed`、`evidence[]`。虚实线只辅助区分关系，具体含义仍由边标签说明，不能从线型推断已经实施。
- 分组：唯一 `id`、`label`、不重复的 `nodes[]`。只支持一层、每节点一个归属；分组背景不能误包其他节点。

## 改前、变更、改后如何对齐

画图前写清比较问题、比较对象、前后版本或时点、画到哪里。能用同一角色和起点比较，就保留同一节点 ID、位置和叫法；职责或结果真有变化才画为变更、替换、增加或移除。局部放大图、并排静态图和独立时序图同样要对齐；相同对象跨图尽量用同名，层级或范围变了就在图旁说明。

1. **对材料校对图义。** 分别沿改前和改后走一遍：从什么触发、经过什么关键步骤或责任边界、产生什么可观察结果。流程图对齐输入、产出与会影响结论的分支；时序图对齐参与方、触发和回应（无应答、异步回执或失败也按实际说明）；架构图对齐系统边界、负责组件、必要调用和职责去向。实际省略、尚不清楚或不再存在的环节要明说，不补猜测的线。比如同一份材料的改写，两侧都交付报告；“打开来源核对”是读者收到报告后的动作。
2. **对实际成品复核。** 分别只看改前、改后，能独立说清该视图的问题和结果；再看变更图，确认它解释前后差异，箭头、标签、结果都能看到。分图还要复查上图产出与下图接续是否对应。对照图旁说明和正文，确保计划没有被当成现状。严格生成只能检查数据结构与已登记节点可见性，不能代替这两步。

## 布局与交互

自动布局用于小型有向无环图，三态共享坐标。可为全部节点显式指定 `column`、`row`（0–30 的整数网格，禁止重复格和部分定位）；循环关系必须全量显式布局，自环暂不支持。它不是通用智能布线引擎。长标签会换行，图可局部横向滚动；作者仍须目检线、标签、边界与字号。

同一对相邻横排单元的两条请求关系会用上下曲线分开，三态保持路线位置；不能把两种关系压成互相遮盖的标签。其余多重平行关系优先按共同机制归并标签；若变化含义或职责不同、无法准确归并，则拆小图或用静态 SVG，不承诺任意平行拓扑自动分线。

按较小而有意义的业务单元拆分，用 groups 框表达组成的模块；同时画出单元之间影响理解的必要请求、依赖或授权关系。核对每个单元的输入、输出或职责关联，避免只罗列孤立盒子。组合关系可由框表示；缺少关系证据时标明未知，不为连通而制造调用箭头。不同性质的关系用准确边标签说明，必要时辅以虚实线和就近短说明；避免把并列能力串成先后调用。节点采用紧凑尺寸；标签变长时先简写或拆单元，不能把框撑大后留大量空白。图例默认展开，读者可手动收起，打印／无脚本保留；状态符号与必要“待实施”边界常显，不再在图下重复列“修改：A→B”与图示依据。改前标签保留在三态和节点 title 中。

仅在真实对比中使用“保留／新增／移除／修改”状态。静态结构或全体 unchanged 的候选图不贴“保留”图例；是否已实施由原材料和 note 说明，不能从静态线框推断。

改前排除新增，改后排除移除，不可见端点的边也排除；变更视图带文字／符号标识。图例只列实际用到的形状、变化、线型及分组。存在变化时，JavaScript 默认选择“变更”，可切换三态，无脚本和打印展示全部三态；全部 unchanged 时只展示一张结构图，不制造相同画面和无用开关。打印图缩放时必须目检文字仍可读；过宽图优先拆分。

`note` 明确比较快照与已实现／待实施的区别，`evidence` 为图示依据，在图标题角标引用，不表示图已经运行。SVG 标签保持安全纯文本；图中专用词若无正文解释，应在 note 或相邻说明复用一次以提供下划线释义，不能仅依赖 SVG title。
